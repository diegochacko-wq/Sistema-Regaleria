He analizado en detalle la estructura de tu proyecto tanto en el repositorio local (sistema-regateria) como en la nube (Renzi's Hub), sin realizar ninguna modificación en el código.

El sistema actual tiene las bases de catálogo y clientes, pero para convertirse en un software POS comercial y confiable para negocios reales, presenta varios cuellos de botella que deben corregirse.

Diagnóstico de Problemas Críticos Detectados

  1. Monolito en cliente y 40 errores de compilación:
    • En page.tsx se concentran navegación, carrito, búsqueda, cámara (jsQR) y componentes (CajaPOS, ModuloDeudas, ModuloSenas).
    • La mezcla de .jsx y .tsx con tipos any[] provoca advertencias y riesgo de fallos en tiempo de ejecución en pleno mostrador.
  2. Falta de integridad transaccional (Riesgo de stock negativo y dinero huérfano):
    • Actualmente las ventas y bajas de inventario se disparan como operaciones separadas desde el cliente. Si la conexión fluctúa o dos cajeros cobran a la vez, se pierde la concordancia entre dinero cobrado y stock disponible.
  3. Seguridad multi-comercio vulnerable:
    • La selección del negocio activo se maneja mediante localStorage y un contexto en el cliente (useLocalStorageNegocio). Si las políticas RLS (Row Level Security) de Supabase no validan la pertenencia en el backend, cualquier usuario con acceso al navegador podría manipular datos de otros comercios.
  4. Módulos esenciales ausentes en base de datos:
    • No existen aún las tablas relacionales para turnos de caja (aperturas y cierres), ventas e ítems, cuentas corrientes (libro mayor debe/haber) ni gestión formal de señas.

Plan de Modificaciones por Prioridad

Prioridad 1: Integridad Transaccional y Núcleo de Base de Datos

  • Qué modificar: Crear las tablas sales, sale_items, cash_shifts (turnos de caja), cash_movements (ingresos/egresos) y una función SQL atómica (process_pos_sale) en Supabase.
  • Por qué: Un POS comercial no puede registrar una venta si no hay una caja abierta, ni puede descontar stock sin garantizar que el pago se asentó. La función en base de datos asegura que la venta, el descuento de stock y el ingreso a caja ocurran en una sola transacción (BEGIN ... COMMIT).

Prioridad 2: Estabilización del Punto de Venta y Experiencia de Mostrador

  • Qué modificar: Migrar todos los componentes .jsx a TypeScript estricto, separar el escaneo físico (lector láser/USB por atajos de teclado sin perder el foco) del escaneo por cámara web, y rediseñar el modal de cobro (efectivo con cálculo de vuelto, tarjetas, transferencias y pagos combinados).
  • Por qué: En atención al público la velocidad y la fluidez son críticas; el cajero debe operar casi exclusivamente con teclado y lector de código de barras sin demoras de interfaz.

Prioridad 3: Módulos Comerciales (Cuentas Corrientes, Señas y Stock)

  • Qué modificar:
    • Cuentas Corrientes: Registrar compras fiadas, pagos a cuenta y saldo deudor histórico con emisión de recibo.
    • Señas / Encargos: Vincular anticipos a pedidos personalizados (muy frecuente en regalería/estampados), con fecha de entrega pactada y liquidación automática del saldo al momento del retiro.
    • Stock y Variantes: Alertas de stock mínimo y trazabilidad de ingresos/egresos con motivo.
  • Por qué: Son las funciones que diferencian una calculadora de mostrador de un sistema de gestión profesional que un comerciante esté dispuesto a pagar mensualmente.

Prioridad 4: Arqueo Ciego, Reportes Financieros y Comercialización

  • Qué modificar:
    • Cierre ciego de caja: El cajero declara lo que cuenta en físico sin ver el total del sistema para evitar manipulación de faltantes/sobrantes.
    • Reportes: Rentabilidad real (precio venta - costo compra), productos más vendidos (Pareto) y flujo de caja diario/mensual.
    • Multi-negocio estricto: Aislamiento de sucursales con perfiles de permisos (dueño, encargado, cajero).
  • Por qué: Da control antifraude a los dueños de negocios y proporciona la base para ofrecer el sistema como SaaS comercializable.

Pasos para aplicar la migración en tu Supabase local o Cloud

Tenés dos formas directas de aplicarla:

Opción 1: Desde el Dashboard de Supabase (SQL Editor)

  1. Abrí el panel de tu proyecto de Supabase vinculado a sistema-regateria.
  2. Andá a SQL Editor -> New query.
  3. Copiá el contenido del archivo migracion_pos_core.sql que te generé y ejecutalo con Run.

Opción 2: Mediante la CLI de Supabase en tu terminal de VS Code

Si tenés instalada la CLI de Supabase en tu máquina:

# Crear el archivo de migración
npx supabase migration new pos_core_schema

# Pegar el contenido del script en el archivo generado dentro de /supabase/migrations/
# y luego aplicar:
npx supabase db push

Script de Validación y Testeo

Una vez ejecutada la migración, podés correr esta consulta en el SQL Editor para verificar que el esquema, los permisos RLS y la función fn_process_sale funcionen exactamente como se espera:

-- 1. Validar que las tablas existan con RLS habilitado
SELECT tablename, rowsecurity 
FROM pg_tables 
WHERE schemaname = 'public' 
  AND tablename IN ('cash_registers', 'cash_shifts', 'sales', 'sale_items', 'sale_payments', 'cash_movements');

-- 2. Crear una caja registradora de prueba
INSERT INTO public.cash_registers (name, location)
VALUES ('Caja Mostrador 1', 'Local Central')
RETURNING id;

-- 3. Probar la apertura de turno con fondo inicial (ej. $10.000)
-- (Reemplazá 'ID_DE_CAJA' con el UUID devuelto en el paso 2)
SELECT public.fn_open_shift('ID_DE_CAJA'::uuid, 10000.00);

-- 4. Probar la venta atómica con fn_process_sale
-- (Reemplazá 'ID_DEL_TURNO' y 'ID_DE_UN_PRODUCTO' con IDs válidos de tu base)
SELECT public.fn_process_sale(
  p_shift_id := 'ID_DEL_TURNO'::uuid,
  p_client_id := NULL,
  p_items := jsonb_build_array(
    jsonb_build_object(
      'product_id', 'ID_DE_UN_PRODUCTO',
      'quantity', 1,
      'unit_price', 1500.00
    )
  ),
  p_payments := jsonb_build_array(
    jsonb_build_object(
      'method', 'efectivo',
      'amount', 1500.00
    )
  ),
  p_discount := 0
);

-- 5. Verificar que el movimiento de caja y el stock se actualizaron
SELECT * FROM public.cash_movements WHERE type = 'venta' ORDER BY created_at DESC LIMIT 1;
SELECT id, name, stock FROM public.products WHERE id = 'ID_DE_UN_PRODUCTO';
